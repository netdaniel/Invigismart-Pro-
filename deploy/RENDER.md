# Deploying Invigismart Pro on Render (single origin)

This is the fastest way to bring `invigismart.online` back up after the old cPanel
node (`156.155.252.98` / `dahost11.vpslocal.co.za`) went dark.

**One service serves everything on one hostname:** the static site
(`index.html`, `landing.html`, terms/privacy, `assets/`) **and** `/api/*`. That is
why `api-base.js` stays `''` (same-origin) and there is no second `api.` host to
keep in sync. The Docker image, `render.yaml` and this guide are all built around
that.

```
https://invigismart.online/            -> landing page   (landing.html)
https://invigismart.online/app         -> dashboard      (index.html)
https://invigismart.online/login       -> landing page + modal
https://invigismart.online/terms|privacy
https://invigismart.online/api/*       -> the Python API
```

---

## 0. Prerequisites

- The repo is on GitHub (`github.com/netdaniel/Invigismart-Pro-`).
- **Commit and push the working tree before deploying.** The Dockerfile does
  `COPY robots.txt sitemap.xml ./`, so those files must be in the repo (they are
  untracked right now — `git add robots.txt sitemap.xml` and commit) or the Render
  build fails at that step. Push everything else you changed too.
- A Render account. The blueprint uses `plan: starter` (~$7/month) because that is
  the cheapest plan that allows a **persistent disk**, and a paywall with SQLite
  resets every licence without one.
- **DNS control that is not the dead cPanel.** The zone is served by the
  registrar's nameservers (`ns1..ns3.clusterdns.co.za`, `ns4.clusterdns.org`).
  Edit records in the **ClusterDNS / registrar control panel**, *not* in the cPanel
  Zone Editor — that host is offline, so its UI cannot be reached.

---

## 1. Create the service (Blueprint)

1. Render Dashboard → **New +** → **Blueprint**.
2. Connect the GitHub account and pick the `Invigismart-Pro-` repo.
3. Render reads `render.yaml` and shows the service `invigismart-api`. Click
   **Apply**.

It will prompt for each `sync: false` value:

| Variable | What to enter |
| --- | --- |
| `APP_BASE_URL` | `https://invigismart-api.onrender.com` **for now** (the URL Render just created). Switch to `https://invigismart.online` after step 3. |
| `PAYFAST_MERCHANT_ID`, `PAYFAST_MERCHANT_KEY`, `PAYFAST_PASSPHRASE` | from PayFast → Settings → Integration. No PayFast yet? Read "First bring-up" below. |
| `ADMIN_TOKEN` | optional; leave blank to keep `/api/admin/overview` disabled. |

`JWT_SECRET` is generated by Render (`generateValue: true`). `HOST`, `DB_PATH`,
`DOCUMENTS_DIR`, the plan copy and the support contacts are already set in
`render.yaml`. **Do not set `PORT`** — Render injects it and the app + health
probe both read `$PORT`.

### First bring-up without PayFast

`server/config.py` refuses to boot when `APP_BASE_URL` is `https://…` and the
payment gateway is not fully configured (a guard against "the school pays and
nothing unlocks"). To get the **site + app online before your PayFast keys
exist**, open the service → **Environment** and set:

```
ALLOW_INSECURE_BILLING = 1
```

Then **Manual Deploy → Deploy latest commit**. The marketing pages, signup and the
roster dashboard work; **payments are OFF** (mock billing is force-disabled on a
public https host). Set it back to `0` as soon as the three PayFast values are
entered, then redeploy — otherwise a real payment cannot complete.

## 2. Wait for the deploy to go green

Render's health check is `GET /api/health` (returns `{"ok": true, …}`). The service
is live when the deploy shows **Live** and the health check passes. Prove the
single-origin app works on Render's own hostname before touching DNS:

```bash
curl -s https://invigismart-api.onrender.com/api/health
curl -s -o /dev/null -w '%{http_code}\n' https://invigismart-api.onrender.com/
curl -s -o /dev/null -w '%{http_code}\n' https://invigismart-api.onrender.com/app
```

All three should return 200 (and the JSON health body). This confirms the pages
**and** the API are served together, exactly as they will be on the real domain.

---

## 3. Attach the custom domain

In the Render service → **Settings** → **Custom Domains**, add both:

- `invigismart.online`
- `www.invigismart.online`

Render shows the exact records to create (step 4) and **auto-provisions TLS
(Let's Encrypt)** once they resolve; HTTP is redirected to HTTPS automatically.

---

## 4. DNS records (at ClusterDNS / registrar — not the dead cPanel)

Replace the records that currently point at the dead host (`156.155.252.98`) and
any stale GitHub-Pages leftovers (`185.199.10x.153`):

| Type | Name | Value | TTL | Notes |
| --- | --- | --- | --- | --- |
| `A` | `@` (`invigismart.online`) | `216.24.57.1` | 300 | Render's load-balancer IP. Keep the TTL low during the move. |
| `CNAME` | `www` | `invigismart-api.onrender.com` | 300 | The service subdomain Render created. |
| `CNAME` | `api` | `invigismart-api.onrender.com` | 300 | Optional: makes `api.invigismart.online` also work (same service). |

Rules that bite if ignored:

- **Delete any `AAAA` records** for `@`/`www`. Render is IPv4-only and an IPv6
  record causes intermittent failures.
- **Delete the old A records** (`156.155.252.98`, `185.199.108/109/110.153`).
  Leaving them lets resolvers hand out a dead (or stale) address until the old TTL
  expires — it was **14400s (4h)**, so this is worth doing first.
- If your DNS provider supports **`ALIAS` / `ANAME` / CNAME-flattening**, you may
  point `@` at `invigismart-api.onrender.com` instead of the `A` record.
- Behind **Cloudflare**: use a **CNAME** (not an A record) for `@`, and see Render's
  *Configuring Cloudflare DNS* guide. Keep proxying off for the apex while Render
  verifies, then you may enable it.

After DNS propagates, Render shows **Verified** on each custom domain. Then go back
to the service → **Environment**, set `APP_BASE_URL = https://invigismart.online`,
and **Manual Deploy**. This value builds the PayFast `return_url` / `cancel_url` and
the recorded `notify_url`, so it must match the address customers see.

---

## 5. Verify end-to-end

```bash
dig +short invigismart.online          # -> 216.24.57.1 (or a Render/Alias answer)
dig +short www.invigismart.online      # -> ...onrender.com chain
curl -s -o /dev/null -w 'apex %{http_code}\n'  https://invigismart.online/
curl -s -o /dev/null -w 'www  %{http_code}\n'  https://www.invigismart.online/
curl -s https://invigismart.online/api/health
./deploy/verify-live.sh --base https://invigismart.online
```

`verify-live.sh` prints one verdict per check (pages, API, env, billing profile). A
fully graded run needs real PayFast keys; with `ALLOW_INSECURE_BILLING=1` it still
confirms the site and API are up and flags billing as unconfigured.

## Operational limits (same as DEPLOY.md, not Render-specific)

- **One instance only.** SQLite + `ThreadingHTTPServer` is a single writer. Two
  instances would each keep a different database and split licences. Never add
  replicas; scale by moving to a real RDBMS + WSGI/ASGI server first.
- **The disk is the paywall.** `/data` (mounted by `render.yaml`) holds the SQLite
  database and uploaded PDFs. Without it, every deploy and idle restart wipes paid
  licences. Keep `plan: starter` or larger.
- **Cold starts.** `starter` stays warm. If you ever drop to `free`, Render sleeps
  after 15 min idle; a PayFast ITN arriving during sleep is retried (PayFast does
  retry) rather than applied instantly.

---

## Rollback / leaving Render

- **Bad deploy:** Render → the service → **Rollbacks** → pick the previous deploy.
- **Back to cPanel later:** point `@`/`www` back to the cPanel IP and re-run
  `deploy/upload-static.sh` + `deploy/upload-passenger.sh` (see `deploy/README.md`).
  Nothing in this repo is Render-specific except `render.yaml`; the app is the same
  standard-library server either way.
